# The Jira token lives in the Forwarder, never in a Run

A Run must call Jira without ever holding the API token. Claude Code's native `sandbox.credentials` masking with `injectHosts` does this, but inside an unprivileged container it needs bubblewrap, TLS termination and `enableWeakerNestedSandbox`, which the docs describe as considerably weakening the sandbox, and the docs do not state whether it applies in `-p` mode. We instead run a localhost Forwarder owned by the Receiver: it holds the real token, replaces the basic-auth header on each request, and forwards to the Atlassian site. Each Run gets a scrubbed environment in which `JIRA_SITE_URL` points at the Forwarder and `JIRA_API_TOKEN` is a per-run sentinel. jira-as uses plain HTTP basic auth through the requests library and accepts an http site URL, so no patching is needed.

## Consequences

- Superseded by ADR 0013: the Anthropic API key stays outside Runs behind a fifth mediated endpoint. The original OAuth credential exception no longer applies to the accepted target design.
- Native masking is a stretch goal to show as the built-in equivalent, not a day-one dependency.

## Amendments

**2026-09-23, from the `/proc` probe (demo-onboarding step 01).** The Receiver holds the real token in its own initial environment, and every Run is its child under the same uid, so the token was readable in `/proc/1/environ` and `/proc/1/task/1/environ`; a live Run read it from the second (probe-2026-09-23.md). The Receiver now marks itself non-dumpable at startup on Linux (`prctl(PR_SET_DUMPABLE, 0)`), and refuses to start if it cannot. Its `/proc` entries then belong to root, and a Run, which holds no capability, can neither read them nor ptrace it, whichever tool asks: Claude's `Read`, whose rule is now scoped as well (ADR 0003's amendment), or jira-as, which opens local files for an attachment upload, a template or a batch file where no permission rule can see. A Run's own `/proc` is unaffected, since exec makes a child dumpable again and a Run's environment holds only its sentinel. On a Mac in laptop mode there is no `/proc` and the call is skipped. The opt-in container check asserts that `docker compose exec demo cat /proc/1/environ` is refused.

What this does not close: the Receiver is not the only process holding the token. Docker gives every process it execs into the container the container's whole environment, `JIRA_API_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` included, and runs it as the same `demo` uid, dumpable. That is the compose healthcheck (a short Python process every 10 seconds) and every `docker compose exec demo ...`, the container check above among them. While one is alive, a Run that guessed its PID could read its `/proc/<pid>/environ` through jira-as's file-reading paths; Claude's `Read` is already scoped away from `/proc`. The window is short and the PID a guess, but the route is real. The lasting fix is to keep the real token out of the container's environment altogether, for example a file the Receiver reads and unlinks at startup, or a Receiver under a different uid from its Runs; it is deferred beyond step 01.

**2026-09-23, the healthcheck (demo-onboarding step 06).** The healthcheck now starts its probe as `env -i /usr/bin/python3 -c ...`. `env` still receives the container's environment from Docker, but only for the instant before it execs Python with none, and a process's `/proc/<pid>/environ` is what its latest exec was given, so the probe that lives for the request holds nothing; a throwaway container of the image showed it empty. That takes the one recurring exec off the route above. Every `docker compose exec demo ...` still carries the token, so the lasting fix stands.

**2026-09-24, the execs that remain (demo-onboarding steps 09 and 11).** Where the route above stands now. The healthcheck, the one exec that recurs, starts its probe through `env -i` (step 06), so the probe holds no environment at all. `doctor --in-container`, which `doctor`'s stack layer runs with `docker compose exec -T demo`, is given the whole environment like any exec, so it marks itself non-dumpable first: before it reads its environment and before its own imports, through `grafana_jsm_sandbox/nondumpable.py`, a module that imports nothing of the package and that the Receiver now uses too. If the call fails it prints one FAIL and stops without reading the environment. What is left is the interpreter's own start-up, from the exec to that call, during which a Run working at the same moment could read the token from its `/proc/<pid>/environ` through one of jira-as's file-reading paths; the package's imports, about 0.45 s where nothing is precompiled as in the container, come after it. Anything else run through `docker compose exec demo`, a shell included, still carries both tokens for as long as it lives, so the lasting fix, the real token kept out of the container's environment, still stands.

**2026-10-01, one create attempt per Run (demo-run findings).** The Skill told a Run that a failed create is final, and the cheapest model ignored it: it ran the same malformed create six times, then changed fields and made an Incident whose Description was `Test`. Prompt text is not a boundary, and every Jira request of a Run already passes the Forwarder, so the Forwarder now counts creates and reads the first. Counting alone would not have stopped that Run: its six malformed creates never reached the Forwarder, because jira-as refuses a `--custom-fields` value that is not JSON before it sends anything, and the create that made the placeholder was the Run's first request. Each sentinel carries one issue-create attempt. A create is a POST to `/rest/api/3/issue`, `/rest/api/2/issue` or `/rest/api/latest/issue`, to their `/bulk` forms, or to the Service Management `/rest/servicedeskapi/request`; the query string is ignored, and a trailing slash, a different case, percent-escapes, path parameters, `.` and `..` segments and doubled slashes read as the same path, because the Forwarder cannot know which of them Atlassian's edge would route to a create. These are every direct issue-create endpoint jira-as 2.0.0 has: `issue create`, `agile epic create`, `agile subtask`, the two `clone` commands and `jsm request create` use them, and so do the `api call` operations createIssue, createIssues and createCustomerRequest. The first create a sentinel presents is the attempt, whatever upstream answers: a 4xx, a 5xx or no answer, since the site may have made the Incident before the connection failed. Before the process starts, the spawner uses incident-payload's pure create-field function with the Run's Notification and rendered project facts, and registers the expected Summary, label set and parsed ADF Description with the sentinel. A Notification with nothing firing registers no create content. The first single-issue create is forwarded only when `fields.summary` and `fields.description` equal the registered values and the set of `fields.labels` equals the registered set. Unjudged fields, including project, issue type, components and custom fields, pass through. A placeholder such as `Test`, even inside a valid ADF bullet list, differs from the registered Description. Bulk and Service Management creates are always refused, even with gate-passing decoy `fields` beside `issueUpdates`. Every refused first create is answered 400 with a Jira-shaped body naming the differing field, absent registration or forbidden endpoint. The Forwarder logs a WARNING `refused a POST ...: this create does not carry an Incident's content (...)`, and spends the attempt without forwarding, so the Run cannot send another. A second create is not forwarded. It is answered 409 with a Jira-shaped body (`{"errorMessages": ["..."], "errors": {}}`) that jira-as prints, saying that the Run already made its one create attempt, and the Forwarder logs a WARNING `refused a POST ...: this Run already made its one create attempt`. A new sentinel starts at zero with a snapshot of its content, and `clear_sentinel` clears both. Checking the sentinel and content and spending the attempt are one step under the sentinel's lock, so creates racing on one sentinel let exactly one through. Comments, label edits, transitions, searches and reads are not counted or changed.

Two effects to know. jira-as's own client retries a POST on a 429 or a 5xx, up to three times; each retry is a second create and is refused, so a Run whose create met a 5xx prints the 409, and the Forwarder's log holds both lines. And jira-as adds its own hint to a 409, "try refreshing and applying your changes again", which contradicts the refusal; the presenter log therefore shows a Run's tool result that carries either refusal as one `[DENIED]` line, naming what a 400 found missing, and the Transcript keeps what jira-as printed. A Run that ends because its create was refused starts its final message `failed: ` in its own words. A successful Finish starts `ok: ` before group text. The formatter reads only the first non-empty line of a `success` result and matches `failed: ` case-sensitively: `ok: failed DEMO-12 created` is successful, and `FAILED: ` is not a failure marker. Claude Code calls a Run that finished its turn `success`, so the formatter turns the failure marker into `[FAILED]`. What this does not do: it counts direct issue creates only. A manual Automation rule can create issues, and a call that invokes one is not counted: jira-as 2.0.0's CLI has no such call (`admin automation invoke` is a retired verb there, and its client method has no command), but a later jira-as that brought it back would reach `/gateway/api/automation/...` through the Forwarder when the site gateway is used. That, and a Run that could create something else (an Assets object, a version, a component), are limited by the account's permissions and the allow list alone (ADR 0003). The gate checks the create content before forwarding. `verify --mvp` also compares the final Incident and comments with the Alerts after later updates.
