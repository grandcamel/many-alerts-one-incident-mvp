# Incidents are keyed by a Fingerprint label and managed with platform operations only

Status: the exact-match rule is superseded by [ADR 0006](0006-one-incident-per-fault-and-match-is-a-judgment.md). The Fingerprint label as an Alert's identity on an Incident, and platform operations only, still hold.

Matching an Alert to an Incident is exact: the open Incident carrying the label `fp-<fingerprint>`, found with `project = OPS AND issuetype = Incident AND labels = fp-<fingerprint> AND statusCategory != Done`. Fuzzy matching on alert name and labels was rejected because Grafana already provides a stable identity, and a resolved-then-refired Alert deliberately gets a new Incident so that chapter two's Problem grouping has something to group. Although OPS is a JSM project, the Run uses only platform operations (search, create, edit, comment, transition), because they are project-keyed and the Incidents queue filters on issue type alone. No servicedeskapi call is needed.

## Consequences

- Chapter two is a label lookup plus one link of type 10006, not a new matching design.
- OPS itself was created from the ITSM template with `createProject` and the project template key `com.atlassian.servicedesk:itil-v2-service-desk-project`, verified 2026-09-14. The `simplified-it-service-management` key the API's enum offers fails with `template does not exist` and is not what OPS was made from. Recreating the project on another site is that one call; afterwards the Skill's field ids (Severity, Urgency, Source) and the Incidents queue id are that site's own and are read from it, not copied from here.
- Completed must set a resolution, or the Incident stays in the unresolved queues. Verified against real OPS issues in ticket 04: the `Resolve` transition leaves `resolution` null on its own, and `jira-as lifecycle transition <key> --id <id> --resolution Done` sets it. It is the only transition on this workflow that accepts one — `Cancel` and `Close` have it rejected by their screens, `editIssue` cannot set it, and `Canceled` has no way out but `Close`. So an Incident parked in `Canceled` sits in the Incidents queue for good, and `Resolve` with a resolution is the only clean exit, for automation and for cleaning up after a rehearsal alike.

## Amendments

**2026-09-24, another engineer's project (demo-onboarding step 11).** OPS is the owner's project, not the demo's. The key now comes from `DEMO_PROJECT_KEY` in `.env`, which has no default, and the Match search is the same with that key in place of `OPS`. Two things above do not carry over to another engineer's site:

- **Creating the project needs a Jira admin.** `createProject` needs the global Administer Jira permission, which a project admin does not hold, and the one call above worked only with a template key the published `createProject` enum does not carry: the key the enum does offer for this template fails. So another site's project is created by its Jira admin from the IT service management template in the Jira UI, and the engineer is made its administrator ([docs/admin-requests.md](../admin-requests.md#jira-admin-create-project)). The field ids and the Incidents queue are then read off that project by `python3 -m grafana_jsm_sandbox.configure`, which writes them to `.env`, never copied from here.
- **The Incidents queue filters on resolution as well as issue type.** The sentence above that it filters on issue type alone is wrong, and the last consequence already says why: an Incident leaves the queue when it gets a resolution, not when it reaches a status in the Done category, which is why Completed must carry one and a resolution-less `Canceled` stays for good. `configure` reads the queue's JQL and warns when it has no unresolved-resolution clause. That the Run needs no servicedeskapi call still holds; only `configure` asks the service desk API, and only to find the queue.
